# Chapter 21 Solutions

## Exercise Solutions

1. **Audit the boundary.** `squad_state_read` and `squad_state_list` inspect state; `squad_decide`, `squad_state_write`, `squad_state_append`, `squad_state_delete`, and `squad_state_create_if_absent` mutate it; the `memory.*` family applies governance, search, promotion, deletion, or audit; `squad_state_health` and `squad_state_upstreams` report configuration/resolution. `squad_state_health` verifies the bridge version, backend, and team directory before the write. A `routing.md` rejection means the API correctly protects static team configuration from a runtime-state mutation path.

2. **Map precedence.** The project's local skill wins over both inherited versions. If no local skill exists, the first declared upstream wins over later declarations. Nested upstreams are visited depth-first immediately after their parent, and a duplicate/diamond source is retained only at its earliest position. The report retains losing skill entries with the provenance of the source that overrode them. Provenance has the form `upstream:<name>@<ref>`; local sources use `@local`.

3. **Exercise soft failures.** The missing local source is reported `missing`; a registered Git source without a materialized cache is `unavailable`. Neither prevents readable sources from being processed. `squad upstream sync <name>` validates local/export paths or fetches/materializes a Git cache. After successful Git sync, the next resolution reads the local snapshot and shows its provenance/status; it does not fetch again on the next session start.

4. **Read the SPI contract.** A cancellation-only adapter should advertise `cancellation: true` and `streaming`, `approvals`, and `tools` as false unless it truly supports them. It implements `submit`, `subscribe`, `cancel`, `respondApproval`, and `describe` because those methods comprise the interface; unsupported operations must fail safely rather than advertise capabilities it does not implement. It deduplicates on `(conversationId, runId, seq)` or stable `operationId`. The built-in MCP bridge has no registered harness and therefore reports `executionAvailable: false`; it refuses message admission instead of creating an unserviceable queued run.

## Quiz Answers

1. Required: `author`, `summary`, and `body`; optional `references` is a string array. It writes a dated note into the decision inbox (or the active workstream's inbox), not directly into the shared decisions file.
2. The check confirms that the bridge runtime version and team root match the coordinator's expectations and identifies the active state backend. A mismatch means writes could go to stale code or the wrong team's state.
3. The local skill wins, then the earliest declared upstream. Upstreams are processed in declared order and each source's nested sources follow depth-first, with a default maximum depth of three.
4. No. Session resolution reads already materialized local paths, Git clones, or export files. `squad upstream sync` explicitly refreshes Git clones and validates local/export sources; there is no implicit network fetch at startup.
5. The process must receive `--experimental-backend` or `SQUAD_EXPERIMENTAL_BACKEND=1`. The URL selects a backend only after opt-in; by itself it must not expose tools or route a token.
6. It implements `submit`, `subscribe`, `cancel`, `respondApproval`, and `describe`. With no harness, the bridge reports an empty harness list and `executionAvailable: false`; send-message refuses as unavailable.
7. Examples: approval hashes are opaque and supplied by the harness rather than broker-computed; epochs are client-asserted rather than broker-issued lease tokens; cursors are unsigned; conversations are whole-file snapshots; there is no bundled execution harness; remote DurableSquad Phase 2 approval/lease coordination is pending.
