# Chapter 21 Solutions

## Exercise Solutions

1. **Audit the boundary.** `squad_state_read` and `squad_state_list` inspect state; `squad_decide`, `squad_state_write`, `squad_state_append`, `squad_state_delete`, and `squad_state_create_if_absent` mutate it; the `memory.*` family applies governance, search, promotion, deletion, or audit; `squad_state_health` and `squad_state_upstreams` report configuration/resolution. `squad_state_health` verifies the bridge version, backend, and team directory before the write; its `Health metadata:` line gives `resolvedTeamRoot` and `resolvedSquadDir`. A `routing.md` rejection means the API correctly protects static team configuration from a runtime-state mutation path.

2. **Map precedence.** The project's local skill wins over both inherited versions. If no local skill exists, the first declared upstream wins over later declarations. Nested upstreams are visited depth-first immediately after their parent, and a duplicate/diamond source is retained only at its earliest position. The report retains losing skill entries with the provenance of the source that overrode them. Provenance has the form `upstream:<name>@<ref>`; local sources use `@local`.

3. **Exercise soft failures.** The missing local source is reported `missing`; a registered Git source without a materialized cache is `unavailable`. Neither prevents readable sources from being processed. `squad upstream sync <name>` validates local/export paths or fetches/materializes a Git cache. After successful Git sync, the next resolution reads the local snapshot and shows its provenance/status; it does not fetch again on the next session start.

4. **Read the SPI contract.** A cancellation-only adapter should advertise `cancellation: true` and `streaming`, `approvals`, and `tools` as false unless it truly supports them. It implements `submit`, `subscribe`, `cancel`, `respondApproval`, and `describe` because those methods comprise the interface; unsupported operations must fail safely rather than advertise capabilities it does not implement. It deduplicates on `(conversationId, runId, seq)` or stable `operationId`. The state MCP bridge cannot load your adapter (it registers only the two bundled harnesses), so unless one of those is registered it reports `executionAvailable: false` and refuses message admission instead of creating an unserviceable queued run. Building on `TurnHarness` gives you shared acceptance for concurrent deliveries, registration before the runtime starts (so an early cancel is kept), an interrupt that finishes before the next turn starts, and restart-safe acceptance and session IDs when you pass a state directory. `TurnApprovals` gives hash-bound, one-at-a-time approvals with redacted summaries, even if you only use it to refuse approvals cleanly.

5. **Check portability.** With an absolute `cli-entry.js` path that exists on this machine, `portable squad_state launch` is a warning ("fails on every other clone"); if the path does not exist (for example a path from another machine), it fails. `squad upgrade` rewrites the entry to `node -e <root finder> .squad/squad.mjs state-mcp` and refreshes the launcher. That form survives a clone because it names only a repository-relative file and `node`; the launcher then finds a Squad CLI on the new machine (`SQUAD_CLI`, project `node_modules`, `squad` on PATH, or the CLI recorded in `~/.squad/cli.json`), and the root finder makes it work from a subfolder.

## Quiz Answers

1. Required: `author`, `summary`, and `body`; optional `references` is a string array. It writes a dated note into the decision inbox (or the active workstream's inbox), not directly into the shared decisions file.
2. The check confirms that the bridge runtime version and team root match the coordinator's expectations and identifies the active state backend. A mismatch means writes could go to stale code or the wrong team's state.
3. The local skill wins, then the earliest declared upstream. Upstreams are processed in declared order and each source's nested sources follow depth-first, with a default maximum depth of three.
4. No. Session resolution reads already materialized local paths, Git clones, or export files. `squad upstream sync` explicitly refreshes Git clones and validates local/export sources; there is no implicit network fetch at startup.
5. The process must receive `--experimental-backend` or `SQUAD_EXPERIMENTAL_BACKEND=1`. The URL selects a backend only after opt-in; by itself it must not expose tools or route a token.
6. It implements `submit`, `subscribe`, `cancel`, `respondApproval`, and `describe`. v2.0.0 ships two experimental harnesses, `ClaudeAgentSdkHarness` (`claude-agent-sdk`) and `CopilotSdkHarness` (`copilot-sdk`). With no harness registered, the bridge reports an empty harness list and `executionAvailable: false`; send-message refuses as unavailable. The Claude harness registers only when its optional SDK and an API credential are present; `copilot-sdk` only when listed in `SQUAD_BACKEND_HARNESSES`.
7. Examples: approval hashes are opaque and supplied by the harness rather than broker-computed; epochs are client-asserted rather than broker-issued lease tokens; cursors are unsigned; conversations are whole-file snapshots; the only harnesses are experimental and keep pending approvals in memory; remote DurableSquad Phase 2 approval/lease coordination is pending; profile promotion is pending.
8. `SQUAD_CLI`, then the repository's `node_modules/@bradygaster/squad-cli`, then `squad` on PATH, then the CLI that last ran `squad init` or `squad upgrade` on this machine; any of the last three older than the version that wrote the launcher is skipped. It falls back to the exact-version `npx` package only when `SQUAD_ALLOW_NPX=1`, because that downloads and runs code; otherwise it fails with install instructions.
