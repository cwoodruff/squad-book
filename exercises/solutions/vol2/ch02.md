# Chapter 2 Solutions

## Exercise Solutions

1. **Solo laptop:** `local` is simplest if state is intentionally versioned; otherwise `squad externalize` keeps it local but outside the checkout. Risks include branch-local state for local mode and no cross-machine sharing for externalization. **Two developers:** `orphan` or `two-layer` can keep state out of feature diffs and share via Git, but writers still need synchronization and conflict handling; two-layer adds commit notes. **Three simultaneous Kubernetes replicas:** do not share the built-in local/orphan/two-layer backend as if it were transactional. Use a genuinely shared, transactional backend and validate its locking/conditional-write semantics; the stock `external-stub` is not that backend.
2. Map normalized Squad keys to blob names. Implement `createIfAbsent` with conditional create such as `If-None-Match: *`; convert a precondition failure to `StateKeyConflictError`. For append, either use a server-side append primitive or use a blob lease/version condition around read-modify-write; plain download-concatenate-upload can lose concurrent appends. On timeout, query the object/version/etag before retrying and surface uncertainty if the outcome cannot be proven. Make writes idempotent where possible and test retry behavior against the actual service.
3. `squad externalize` relocates most state to a per-machine OS application-data directory and leaves a local marker. `stateBackend: "orphan"` uses a Git branch as the durable state store. An Azure `StorageProvider` is an SDK implementation of a generic I/O contract that must be injected into a consumer; it is not automatically selected as the CLI’s state backend.
4. A useful record includes stable timestamp, agent and spawn identity, original task, completion status, concise summary, modified-file list, validation results, and the full response or durable reference to it. Persist immediately after collecting the result. Keep the evidence available, but separately curate reusable decisions/skills; do not promote all transcript text, secrets, or irrelevant project details into permanent memory.
5. The interface contains 13 async methods and 12 deprecated sync compatibility methods (25 required methods total). Missing reads return `undefined`; create-if-absent collisions throw `StateKeyConflictError`; unknown create outcomes throw `StateBackendUncertaintyError`; ordinary provider failures may throw `StorageError` or provider-specific errors. Prefer direct reads to check-then-read, use atomic create for one-writer-wins behavior, and handle each error according to its semantics.

## Quiz Answers

1. The Git-aware `StateBackend` chosen by config and used by Squad runtime state operations.
2. `local` (`WorktreeBackend`).
3. It writes to platform-local storage for one machine, not to a shared remote or synchronized service.
4. Conflict means the key definitely existed; uncertainty means the backend cannot determine whether creation succeeded. Inspect state before retrying uncertainty.
5. Another process can change the path after the existence check and before the subsequent operation, creating a time-of-check/time-of-use race.
6. The built-ins are filesystem, in-memory, and SQLite. The sql.js-backed SQLite provider loads and persists the DB in one process and warns that simultaneous multi-process access may corrupt data.
7. A native atomic conditional create: exactly one caller succeeds, existing contents are never overwritten, and ambiguous outcomes are surfaced instead of misreported as success.
8. The orchestration log preserves agent work/results across context loss. It is an evidence archive; durable curated memory is selected and distilled knowledge intended to guide later work.
