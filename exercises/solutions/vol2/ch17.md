# Chapter 17 Solutions

## Exercise Solutions

1. **Classify a claim.** The manifest assigns capabilities independently, and a case exercises only the operations it declares. Passing a validator case proves the documented validation behavior, not serialization/editing or runtime compilation. The manifest does make Charter v0.1 an executable normative working draft with immutable claim revisions, but the suite index's publication status is still `working-draft`; claimability and publication are separate.

2. **Find a routing mismatch.** The draft says equal-priority matches are ambiguous and must fail; the implementation sorts by its computed specificity and returns the first matching rule, so it does not provide the same tie failure. The draft calls for a declared fallback and `route-unresolved` if absent; `matchRoute()` currently returns `@coordinator` when it has no matching rule and no configured fallback. Suitable fixtures include two matching rules with identical priority and an expected ambiguity error, and a no-match input with no fallback and an expected unresolved result plus coordinator/human disposition.

3. **Trace state to provider.** The neutral transition requires an expected work revision and evidence that provider integration succeeded; a neutral record should identify the resource and resulting revision. The GitHub binding maps integration to the PR merge commit or squash/rebase result, evaluates a canonical snapshot including repository/issue/PR identities, head/base SHAs, reviews/checks, owner labels, dependencies, and ruleset observation, and requires a fresh read before mutation. Transcript cases should include a stale head SHA and merge conflict; other useful cases include a secondary rate limit, already-merged retry, partial mutation, or provider drift.

4. **Separate preference from permission.** Charter preserves `auto` as an authored request for runtime selection and validates `high` as an allowed reasoning preference. An unavailable model may remain authored text but cannot be claimed executable without runtime support; invalid Charter input must not be applied. The execution-preferences profile would keep requested versus selected model, source, availability, authorization, and policy disposition separate, and would report unavailable or unauthorized instead of silently exceeding fallback constraints. Authorization comes from the execution environment/provider policy, not from charter prose, a route, or a role label.

5. **Audit the absent documents.** State that those names are not present in the v1.1.0 specification directory or mapped coverage list, so no purpose, requirement language, implementation status, or deviation can be asserted from this source set. Before adding them, confirm the repository and exact tag/commit, inspect the tree for the path and its registry entry, check whether another branch or release contains it, and obtain the actual document. Do not infer the contents from a filename or add a non-existent source URL to Further Reading.

## Quiz Answers

1. A profile is a versioned contract for an artifact or behavior surface. A capability identifier names one operation of that profile, such as `squad-charter/v0.1/validate`.
2. `executable-normative-draft` is the only claimable maturity represented by Charter in this suite. Claimable does not mean published: Charter remains a working draft.
3. False. Dependencies establish interpretation/order; they do not confer capabilities or conformance claims transitively.
4. `accepted` means a consumer may accept the document, including compatible legacy input. `conforms` means it is canonical for the selected profile; warnings can leave a document accepted but nonconforming.
5. Examples include canonical snapshot digest and compare-before-mutate behavior, API-version evidence, idempotent retries, provider-drift handling, precedence for simultaneous conditions, or sanitized deterministic transcripts.
6. A JSON schema validates that fields have the expected shape. It cannot authenticate an actor, prove that a provider identity is genuine, or evaluate whether the authority basis and policy actually permitted the operation.
7. `state-memory-requirements-v0.1.md` is informative and non-claimable. It separates state-authority promotion from memory-classification/provider-dispatch promotion.
8. `client-harness-adapters`, `client-backend-decoupling`, and `ADR-001` are not present in the v1.1.0 specification tree covered by this chapter.
