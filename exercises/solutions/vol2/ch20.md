# Chapter 20 Solutions

## Exercise Solutions

### 1. Intersect the actual token sets

OpenCode advertises all four tokens mentioned in the backend grant. Policy retains only `cancel-run` and `mcp-bridge`, so the effective set is:

```json
["cancel-run", "mcp-bridge"]
```

The helper preserves client advertisement order, not the order of your policy list. Replacing policy with `[]` yields `[]`. Omitting policy instead retains every token allowed by both client and backend, giving `approvals`, `cancel-run`, `mcp-bridge`, and `subagents` in client order.

Do not confuse a missing restriction with a backend explicitly denying all capabilities. These are different inputs even though an unbound facade reports empty backend/policy fields in its descriptive output.

### 2. Add a tolerant inspection mode

Replace the strict normalization step with the following code and import `normalizeClientIds` from the canonical `/client` entrypoint:

```ts
const { clients: known, rejected } = normalizeClientIds(config.clients);
const counts = { 'non-string': 0, sensitive: 0, unknown: 0 };
for (const entry of rejected) counts[entry.reason]++;
console.log(JSON.stringify({ known, rejectedByReason: counts }));
if (known.length === 0 && rejected.length > 0) {
  throw new Error('No recognized clients; refusing a misleading default report.');
}
const clients = known.length ? known : normalizeClientIds(['copilot']).clients;
```

Do not log `config`, raw rejected inputs, or original strings. This adaptation is intentionally JavaScript-compatible syntax, matching the chapter's directly runnable `.ts` example.

Strict mode uses `assertPortableClients`: it rejects non-array input, unknown/sensitive/non-string entries, and duplicates. It does normalize case and whitespace; it is not a literal-casing assertion. Tolerant mode reports known normalized IDs and rejection counts, and de-duplicates them. The explicit check above prevents a future-only client configuration from silently becoming a Copilot-only report. A more complete audit should also distinguish a malformed/non-array `clients` value from an intentionally absent property, because normalization treats non-arrays as an empty selection.

The CLI's forward-compatible persistence layer can preserve unknown portable IDs with `extractUnknownPortableClientIds`; this inspection code does not write configuration and has no reason to persist anything.

### 3. Remove Claude while retaining Copilot

Start a fixture with:

- `.mcp.json` containing a user server, preserving a captured baseline;
- `.gitignore` containing an existing user-authored `.claude/worktrees/` line;
- `CLAUDE.md` containing user guidance;
- an initialized canonical Copilot agent from the CLI bootstrap path.

Install both projections, inspect every result, then remove Claude with:

```ts
const results = uninstallClients(['claude'], ctx, ['copilot']);
```

Assertions should show that `.claude/agents/squad.md` is removed, only the managed block is stripped from `CLAUDE.md`, and the user-authored ignore line remains. Because it existed before installation, the line was not added under a new `# squad:claude` ownership marker. If there are other user ignore rules, retain them too.

The shared `.mcp.json` keeps both the user server and `squad_state`, because Copilot still projects that JSON path. The canonical `.github/agents/squad.agent.md` remains: the SDK Copilot projection does not own it in the first place. `.squad/` state is untouched.

Finally, reconcile persisted `clients[]` separately if the removal should survive a later upgrade. `uninstallClients` edits projected artifacts, not project configuration. A test that forgets the third argument could accidentally accept removal of Copilot's bridge.

### 4. Specify an eighth-host acceptance fixture

This is a source-contribution design, not a call to a nonexistent plugin registration API. Define the host's anchor, MCP manifest schema, marker-scoped discovery file, native dispatch primitive, and honest capability tokens. Extend the SDK's ID, capability, host-kind/anchor, and CLI-selection registries consistently.

Use a JSON projection for the shared manifest and a block projection for the pointer. Assert that an existing user server and unrelated top-level settings survive, that two installs are idempotent, and that uninstall removes only owned keys and the owned pointer. Also test retaining shared paths when another installed host still needs them.

Refusal cases include malformed JSON, a non-object server container, and an unclosed discovery marker. Additional useful cases are a scalar Squad server entry, commented JSONC, path traversal, and symlinked directory components escaping the projection boundary.

One byte-level limitation is JSON reserialization: a minified original may become pretty-printed and uninstall does not retain a snapshot to reverse that transformation. Capture original bytes and compare deliberately; require an explicit backup/snapshot mechanism if arbitrary byte-exact rollback is a product requirement. Do not infer this guarantee from the existing suite's selected byte-exact round-trip fixtures.

### 5. Choose an audit host and prove the outcome

Claude Code or OpenCode is a reasonable choice because both have recorded live evidence for independent specialists and state-tool use in this preview. Copilot is also defensible when it matches your deployment and local validation. Their advertised background capability does not force your audit to permit it.

Use a backend grant that includes `subagents` and `mcp-bridge`; use a policy allowlist including those tokens but omitting `background-runs`. Add `approvals` only if the workflow needs approval interactions and policy permits them. Preserve the decision record through the normal state bridge rather than treating approval capability as persistence authority.

Before execution, authenticate the chosen host, verify the MCP configuration and required project approvals/trust, check state health/version/root, and bind the actual runtime if using the SDK facade. An inspection-only factory without `runtime` cannot execute the audit.

Collect evidence that the API and frontend specialists actually ran, received their charters, and returned results without background dispatch. Observe successful state-tool calls recording the audit decision, then read the result back. A model's narrative that it wrote a decision is insufficient. Report account/quota blockers separately from unsupported features.

## Quiz Answers

1. The implemented `HostProjection` has synchronous `project(ctx)`. `createClientAdapter({ host, ctx, runtime? })` constructs the runtime facade. The draft's illustrative projection SPI differs from that implemented interface.
2. The token describes resuming a transcript/event subscription from a cursor. It is declared across the seven hosts and is not a product selector.
3. An omitted policy list supplies no restriction in the local helper; an explicit empty array removes every token. The same distinction applies to backend lists.
4. No. Without a binding, the facade uses absent restrictions and returns the advertisement as its effective list. Runtime submission still throws `AdapterUnboundError`, and no backend authorization took place.
5. The coordinator reads the selected member's charter and includes it in that specialist's delegation prompt. Projection embeds the coordinator digest and dispatch instructions, not a compile-time copy of every charter.
6. Pass remaining hosts as the third `keep` argument: `uninstallClients(['claude'], ctx, ['copilot'])`. Persisted client configuration must be reconciled separately if intended.
7. Expected-failure tests establish that a required projected coordinator section is missing. They validate the gap rather than validating successful feature execution. Support status and evidence strength are independent axes.
8. `/clients` preserves the same host adapter exports and runtime references as a deprecated alias. It does not create another registry, implement another backend, add execution harnesses, or re-export the older session client classes supplied by `/client`.
