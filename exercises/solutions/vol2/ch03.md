# Chapter 3 Solutions

## Exercise Solutions

1. Example manifest: `name: platform-squad`, capabilities `kubernetes` and `observability`, contact repo `org/platform`, labels `cross-squad` and `needs-triage`, accepts `issues`. The current validator checks nonempty name and repository, arrays for capabilities/accepts, and only `issues`/`prs` acceptance values. It does not enforce capability vocabulary, label existence, repo syntax beyond nonempty string, or whether the peer truly owns the stated scope; those need policy/CI or review.
2. The CLI resolves the current Squad directory, discovers manifests, finds the exact name, checks `accepts` includes `issues`, builds a title/body and labels, then executes `gh issue create --repo ...`. Preconditions include a reachable valid manifest, correct contact repository, GitHub CLI installed, authentication, issue-create permission, and valid labels. The receiving repo still controls triage and completion.
3. (a) Export/import or manually cherry-pick the skill; (b) peer manifest and issue delegation; (c) SubSquads using labels and folder scope; (d) distributed-mesh skill with a deliberately published status summary and authenticated/public transport as appropriate. Upstream inheritance is suitable for top-down policy, not peer work intake.
4. Summaries reduce stale, irrelevant context and limit exposure of secrets or project-specific transcript data. Synchronization is eventual, so each summary should carry freshness information and critical decisions should be checked against canonical issues/repositories. Write partitioning avoids clobbering: each Squad should publish only its own files.
5. Define `api` and `web` entries with required `name` and `labelFilter`, optional `folderScope`, and a workflow of `branch-per-issue` or `direct`. `SQUAD_TEAM` wins first; then `.squad-workstream`; then a single configured entry auto-selects; with multiple entries and no selector, no active SubSquad is resolved.

## Quiz Answers

1. `name`, `capabilities`, `contact.repo`, and `accepts`; `contact.labels` shapes routing/triage.
2. `.squad/squad-registry.json`; entries contain a name and a local filesystem path to the peer repo root or `.squad` directory.
3. No. It inspects configured upstream sources and local registry entries/caches; there is no global repository crawl.
4. The current CLI invokes GitHub CLI (`gh issue create`).
5. The schema allows `prs` as an accepted metadata value, but current `delegateCommand` requires `issues` and only constructs an issue-create call.
6. A SubSquad partitions work within a repository via labels, optional folder scopes, and workflow selection. A separate peer Squad has its own repo/backlog and is discovered through a manifest; it retains independent ownership and governance.
7. It provides bundled scripts and a `mesh.json`-based pull/publish pattern using Git and/or HTTP. It is asynchronous/eventually consistent, not real-time messaging or a transactional distributed store.
8. `multi-squad.ts` selects among named personal Squad state directories under the global config root. It does not discover or delegate work to peer repositories; peer discovery is handled by manifests and the cross-squad runtime module.
