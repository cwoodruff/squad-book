# Chapter 23 Solutions

## Exercise Solutions

1. Example: “Add status tags to Tasktrack tasks. Acceptance: a valid tag is returned by `GET /tasks`; a task can be filtered by an exact tag; unknown tags return an empty list. Do not add a tag-management UI or a database.” Answers vary, but should include testable outcomes and an exclusion.
2. A strong response names the field, its type and null/omission behavior, the owner of each code boundary, and a required handoff. For example: “First agree that `dueDate` is an ISO date-only string or `null`. Backend owns API and validation; Frontend owns display; Tester writes contract cases. Publish the agreed example before implementation.”
3. Check the current repository and working directory; GitHub authentication and repository access; whether the issue is open and eligible; the issue title/body/labels; and the active routing/configuration. Also inspect the scan output and current concurrency/timeout settings. A good answer uses at least five and does not jump directly to execution.
4. Do not silently overwrite the old decision. Record the new date-only requirement, explain why it supersedes the timestamp convention for this field, identify affected API/storage consumers, and open or link a migration task. Preserve timestamp semantics where they still apply.
5. Example: “Premature fan-out” may show up as conflicting edits to the same API schema; recover by pausing implementation, assigning one contract owner, and redispatching by boundary. “Unchecked done” may show up as no test output; recover by running the focused suite and inspecting the diff against acceptance criteria.
