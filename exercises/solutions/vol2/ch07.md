# Chapter 7 Solutions

## Exercise Solutions

1. The repository Dockerfile creates a self-contained standalone bundle in a builder stage and copies it into the runtime image. The reference page's alternative installs `@bradygaster/squad-cli` globally through npm. The bundle avoids an npm-registry dependency at runtime and includes the platform CLI; the trade-off is that the build needs the full source/workspace and the container must be rebuilt to update the bundle. Both examples need image provenance and a digest-pinned base in hardened deployments.
2. AKS workload identity federates the Kubernetes service account to Azure. That Azure identity authenticates to Key Vault and is authorized to read the GitHub token secret. The container receives the GitHub PAT or App installation token from the secret provider. The GitHub token, not the Azure identity token, authenticates the API call to GitHub.
3. Set `SQUAD_DEPLOYMENT_MODE=squad-per-pod` and give each worker a deployment-supplied `SQUAD_POD_ID`. Each manifest should be complete: the GPU worker lists `gpu` and the CPU-only worker does not. A `needs:gpu` label makes the CPU worker ineligible locally, but an external scheduler or queue must dispatch the issue and prevent duplicate claims. With a malformed pod-specific file, lookup continues to the shared team file and then the Squad-home file. With no pod ID, the pod-specific candidate is skipped, so a shared or home manifest may still be selected.
4. A simplified target-based estimate is ceil(17/5) = 4 replicas, then the maximum caps it at 3. Actual KEDA output can differ because of the scaler metric definition, polling interval, cooldown, trigger activation threshold, HPA behavior, issue claim/filtering, and API or authentication errors.
5. The example ScaledObject targets `squad-agent-deployment`, while the Deployment is named `squad-agent`; scaler examples also differ in gRPC port and metadata names. Verify the exact external scaler release, protocol, metadata/authentication fields, and actual resource names. The v1.1.0 repository has `templates/keda-scaler.md`, not the referenced `templates/keda/scaler-deployment.yaml`.
6. `src/squad/handlers.ts` uses deterministic text heuristics rather than `SquadClient` or live model calls. The HTTP trigger is `authLevel: 'anonymous'`. Add authentication, rate limiting, request-size and timeout limits, data retention and privacy controls, real safe execution, telemetry, cost limits, and deployment-specific secret handling before exposure.

## Quiz Answers

1. No. The image should contain no token. Supply a least-privilege GitHub credential at runtime through an approved secret mechanism.
2. It is a unique pod identifier used in the `squad-per-pod` topology. It does not authenticate the pod, authorize GitHub access, provide a work lock, or make local state concurrency-safe.
3. `agent-per-node`; any unset or unrecognized value falls back to this default.
4. No. The two deployment modes select capability-manifest lookup topology; they are unrelated to the interface used to interact with Squad.
5. No. Azure identity authenticates to Azure services. A PAT or GitHub App installation token is still required for GitHub API access.
6. Shared filesystem persistence preserves files but does not provide application-level locking, transactions, or safe concurrent writes for the local backend.
7. The loader selects the first parseable candidate; it does not merge manifests. Without a pod ID, the pod-specific candidate is skipped and shared/team or home candidates may still be selected.
8. No. Capability filtering determines local eligibility only. An external scheduler or queue must distribute work and prevent duplicate claims.
