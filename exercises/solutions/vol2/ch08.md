# Chapter 8 Solutions

## Exercise Solutions

1. `npm test` should pass all five `node:test` cases. The local Docker image should build without dependency installation. `GET /health` returns `{"ok":true}`. The `TaskStore` is in memory, so tasks disappear when the container stops; the sample has no persistence layer.
2. A separate publishing job should run only on a protected default-branch/tag or an approved release event. Keep the test job read-only; grant the publishing job only the registry/package write permission it needs. Use a scoped short-lived identity or protected secret, immutable version/digest tags, provenance/attestation and vulnerability checks, and require human approval through a protected environment or release review. Do not run it for an untrusted fork PR.
3. Select an approved 40-character source SHA, add the complete native package, inspect the safe-update report, strictly compile, verify package ownership and source/lock hashes, stage only reviewed files, open a bootstrap PR, inspect it as an explicit first-install trust boundary, and merge only after human approval. The post-merge activation/Cast output is a second reviewable result. Independent human approval and repository branch protections remain mandatory.
4. Insider starts from `dev`, uses `X.Y.Z-insider.N` and npm tag `insider`; preview starts from `dev`, uses `X.Y.Z-preview.N` and npm tag `preview`; stable is promoted to `main`, uses `X.Y.Z` and npm tag `latest`. Verify the GitHub Release, exact npm dist-tags, archives/checksums, and corresponding Homebrew/WinGet updates.
5. Do not recreate or move the tag or GitHub Release. Rerun the failed publication job or dispatch it from the immutable tag/source ref using the documented recovery path. Then verify SDK and CLI dist-tags match the version, release archives/checksums are present, and package-manager updates or PRs exist. Record any follow-up issue without changing the release identity.

## Quiz Answers

1. Tests need to read source; they do not need to push commits, publish packages, or modify workflow settings. Read-only permission limits the impact of a compromised dependency or test step.
2. `.github/workflows/squad-ci.yml` is a conventional Actions workflow in the repository. `workflows/` contains the separate GH-AW package with Markdown workflow sources, package manifest, runtime resources, and generated/verified locks when installed into a consumer repository.
3. A full SHA identifies one immutable package revision. A branch or tag can move, making a repeated install produce different workflow code without an obvious revision change.
4. Compilation checks syntax and generated workflow integrity, not whether permissions and behavior are acceptable for a particular repository. The bootstrap PR introduces privileged automation and must be reviewed by a person.
5. GitHub commonly suppresses follow-on workflow runs caused by the default `GITHUB_TOKEN` to prevent recursion. The release workflow explicitly dispatches its next stage when needed; otherwise use a deliberate, separately approved trigger mechanism.
6. Rerun the failed publisher or dispatch it from the existing immutable release tag. Do not recreate or move the tag. Verify npm package tags, release assets, checksums, and package-manager outputs afterward.
7. No. It runs tests and builds a local image in CI. It has no image push, registry credential, or cloud deployment step.
