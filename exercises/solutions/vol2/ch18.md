# Chapter 18 Solutions

## Exercise Solutions

1. **Map the planes.** The client parses the user's host-specific request and dispatches the coordinator through that host's tools. The coordinator and broker/control contract establish the conversation, sequence its events, apply policy, and persist the shared state. The execution plane runs the task through a host subagent or registered harness, invokes tools, and returns results. Switching from Copilot to Claude Code may change dispatch syntax and projected files; it should not change the specialist's shared charter, the agreed team policy, or the meaning and order of durable conversation events.

2. **Plan a two-host projection.** For a Claude Code projection, expect `.claude/agents/squad.md`, the managed `CLAUDE.md` pointer/instruction block, `.mcp.json`, and a managed ignore entry for `.claude/worktrees/`. The same `.squad/team.md`, charter directories, decisions, and routing remain authoritative. Generated files let Claude Code discover and run Squad according to Claude conventions; they do not define a second Claude-only roster. Choose the exact client ID explicitly and review additions to shared files.

3. **Write a migration checklist.** Replace client imports with `@bradygaster/squad-sdk/client`; keep the old `clients` alias only during a transition. Import backend interfaces from `@bradygaster/squad-sdk/backend`, not the root package. For state MCP, pass `--experimental-backend` or set `SQUAD_EXPERIMENTAL_BACKEND=1`; do not rely on `SQUAD_BACKEND_URL` to enable it. Instantiate `DurableHttpSquadBackend` with explicit `baseUrl` and optional token, using HTTPS except for loopback. Write `team.md`, `routing.md`, `config.json`, and charters through the workspace/appropriate CLI rather than `squad_state_write`; keep `.squad/casting/` out of hand-edit workflows. Verify with a type-check/import test, inspect the MCP server configuration, test URL validation, and confirm static files are edited in version control.

4. **Audit the security proposal.** Example answers include broker-issued lease identity, signed cursors, and command/argument validation in merged MCP config. Broker-issued lease identity would stop an arbitrary same-user caller from taking over by presenting a larger epoch; preview epochs are cooperative and caller-asserted, so they only fence stale work. Signed cursors would make positions tamper-resistant; preview cursors are opaque but unsigned and are not authorization tokens. Validating command/args would reduce the risk of unsafe launch specifications from config; preview merging preserves data and scopes writes but does not validate shell-sensitive content. Any three earn credit when the answer distinguishes correctness safeguards from security boundaries.

5. **Resolve upstream order.** The local project's value wins first. When upstream values conflict with each other, `org` wins over `team`, which wins over `legacy`, because earlier entries win. The old later-wins documentation would have produced `legacy` as the winner. To migrate safely, run `squad upstream sync`, inspect which rules conflict, then use upstream remove/add to reorder entries so the intended source appears first; preserve the repository's local rule if it should override all inherited choices.

6. **Try the preview safely.** The version command should identify the installed CLI as `2.0.0-preview.2`. Copilot-only init should create shared `.squad/` content plus Copilot integration, including `.github/agents/squad.agent.md` and `.mcp.json`, but no non-Copilot projection directories. The `squad roster add all --dry-run` output should show the insertion without writing. The actual `squad roster add all` should add only Rai and Fact Checker rows, write a verified backup and provenance record, and show those changes in the Git diff. Exact incidental files vary with the CLI's full project-init behavior; the key assertions are version, explicitly selected host, and no unrequested host projections.

## Quiz Answers

1. One repository-owned `.squad/` team can be used through multiple host-native integrations without keeping separate, drifting team definitions. Host files are projections, while the roster and charters stay shared.
2. **Client plane:** host configuration, UI/event adaptation, and dispatch. **Control/broker plane:** conversation identity, ordering, approvals, capabilities, cancellation, and durable history. **Execution plane:** workers, tools, checkpoints, retries, and task execution.
3. Intersection ensures a capability is effective only if the host offers it, the backend supports it, and policy permits it. A union would incorrectly claim a feature when any necessary layer lacks it or disallows it.
4. No. The bridge exposes the backend tools only when started with `--experimental-backend` or `SQUAD_EXPERIMENTAL_BACKEND=1`; `SQUAD_BACKEND_URL` by itself does not enable them. The bundled bridge has no execution harness, so it is not a turnkey hosted agent runtime.
5. Squad no longer finds or falls back to a profile-level personal/global team; resolution is project-local, walking from the current directory through parents and respecting repository boundaries. Run `squad init` in the project or use `--team-root <path>` where supported to select an explicit team root.
6. Local project configuration wins; then earlier upstream entries win over later entries. Run `squad upstream sync` after upgrading and reorder configured sources if you relied on the prior later-wins behavior.
7. Run `squad roster add rai` (or preview it with `--dry-run`). Upgrades preserve `team.md`; the explicit command inserts the optional built-in row and records a verified backup and provenance so later removal can target only its own change.
8. No. Epochs are cooperative, client-asserted fencing values that reject stale writers, but any caller able to present a larger value can take over. They have no broker-issued holder identity or expiry and are not an authentication/authorization boundary.
