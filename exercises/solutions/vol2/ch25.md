# Chapter 25 Solutions

## Exercise Solutions

1. Inspect the checked-out root `package.json` scripts and the CI workflow, then run the documented root command in a clean checkout. For the v1.1.0 snapshot, `npm run build` builds both workspaces and CI uses it. Report that the docs-site guide lists `build:cli` while the root scripts do not expose that command. Include the exact file paths and avoid claiming the docs command works unless a package-level script proves it.
2. A strong report includes `squad --version`, OS, Node version, exact `squad init` invocation and working directory, preconditions, expected generated state, actual output/state, minimal reproduction, and whether it happens on a clean project. Redact access tokens, private URLs, user data, and internal prompts.
3. Preserve uncommitted changes, fetch `upstream/dev`, and move the work onto a branch based on `dev`. Depending on how divergent the branch is, rebase the feature commits onto `upstream/dev` or create a fresh branch from `dev` and cherry-pick only the intended commits. Inspect the diff, rerun checks, and use `--force-with-lease` if updating an already-pushed fork branch. Do not merge `main` into `dev` as a shortcut.
4. Read the current path-specific changelog gate and PR checklist. Add a regression test covering the intended behavior and a changeset or accepted changelog entry if required for the CLI source path. Run build, tests, type checks, and relevant lint; inspect the full diff and open a draft PR to `dev` linked to the issue.
5. Preview is a prerelease from `dev` using a `X.Y.Z-preview.N` version via manual dispatch of `squad-release.yml`. Insider is a separate `X.Y.Z-insider.N` npm publication from `dev` via the manual `squad-insider-publish.yml` workflow. Stable is `X.Y.Z` on `main`, after validated promotion through `squad-promote.yml`; `squad-release.yml` creates the GitHub release/tag from the stable line. These are distribution channels, not branches.
