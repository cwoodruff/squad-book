# Chapter 24 Solutions

## Exercise Solutions

1. Example: “Add tags to tasks. A tag is a trimmed string of 1–30 characters; duplicates are case-insensitive; a task may have zero or more tags. `GET /tasks?tag=...` returns exact matching tasks. Existing tasks without tags continue to work. Acceptance tests cover create, duplicate normalization, invalid length, filtering, and the empty result. Out of scope: tag administration UI.”
2. A strong prompt asks the team to inspect the actual store, tests, and API before recommending a persistence design. It names data migration and recovery as open decisions; forbids silently adding a dependency or changing the contract; and requests a PRD before code. The writer should not assume the sample's in-memory store can be replaced without compatibility review.
3. The checklist should prove accepted valid dates, rejection of invalid input, unchanged behavior when the optional field is absent, API response shape, frontend formatting, passing tests/CI, a scoped diff, and no credentials or private data in logs/responses. A human must review and approve the PR.
4. `/health` is Tasktrack's endpoint and demonstrates that its API responds according to the route's contract. `squad health` diagnoses Squad team/configuration state. An OTel trace records an instrumented operation and timing/context. None alone proves feature correctness, all user journeys, or production availability.
5. Example gate: identify the image by immutable digest, require green CI and container health check, have a human approve the production rollout, verify the live health endpoint and a smoke-test operation, and retain the prior image digest plus a rollback procedure.
