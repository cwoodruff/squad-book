# Chapter 4 Solutions

## Exercise Solutions

1. **Portability inventory.** `team.md` is usually a review candidate: names and role split can transfer, but role coverage may depend on the target repo. A narrowly phrased reusable skill is a strong candidate; a skill that refers to Tasktrack paths is not. A routing rule is review-required because path patterns and ownership differ between projects. A decision needs review because it encodes trade-offs and may cease to apply under a new architecture. A history note is review-required unless explicitly generic, and old file paths/PR references are project-local. The Tasktrack source tree itself is not team knowledge; it is application code and should move through normal Git/project workflows.

2. **Safe fork.** `squad export --out ../tasktrack-team.json`, inspect the JSON, then import into a fresh repo with `squad import ../tasktrack-team.json`. The bundle uses manifest version `1.0`; count entries under `agents` and `skills`, and inspect `casting.policy` to see whether it is present. Imported histories are prefixed with import provenance and passed through `splitHistory`, which preserves project learnings under a distinct section when recognized. `--force` renames the old target `.squad/` to a timestamped archive and writes the incoming team; it does not merge them.

3. **Upstream threat model.** Use a Git upstream in a controlled organization repository so there is an auditable source, access control and review history. Assign policy ownership to the security/platform group; pin an explicit branch or tag according to whether consumers should receive continuous updates or a reproducible snapshot. Specify a fallback: if the upstream is unreachable, use last-reviewed committed local policy or stop the workflow for policy-sensitive work. Verify source sync, resolver output, and actual coordinator prompt/application. Read-only consumption avoids downstream repositories silently rewriting the central standard; proposed changes should go through the policy source's review process.

4. **Conflict semantics.** `resolveUpstreams` iterates the configured list and returns one `ResolvedUpstream` per entry, preserving names and order. The resolver does not combine duplicate rule keys or inspect the consumer's local `routing.md` to establish a precedence winner. The guide's later-wins/local-wins claim is not demonstrated by this implementation. A safe implementation can explicitly concatenate/annotate rules with source labels and ask a policy layer to resolve them, or add a test around the consumer's actual merge function that proves the intended precedence. Until that is done, claim only that sources are resolved in an order, not that conflicts are resolved.

5. **Export review checklist.** Confirm the bundle schema/version and source CLI; enumerate all histories, charters, decisions, routing and skills; search manually for credentials, personal data, customer names, internal paths and project-specific references; remove unnecessary material and regenerate; check partner access and retention; transfer the file through an approved channel; import into a fresh test repo; verify files, casting, skills and agent names; inspect history split quality; run `squad status` and a small representative prompt; retain or delete the source bundle according to policy.

## Quiz Answers

1. **Snapshot import.** It creates a copy that can evolve independently. An upstream is a separately configured source.
2. It archives the current `.squad/` directory with a timestamped suffix and replaces the active team with imported state. It is not a merge.
3. No. The exporter includes histories and warns the operator to review the content. History splitting happens during import and is not guaranteed sanitization.
4. Local directory/path, Git repository, and JSON export file. Sync validates a local path; validates that an export file exists; or pulls/reclones the cached Git source and updates sync metadata. It does not merge policy or refresh the contents of an export snapshot.
5. No. It returns separately named upstream result records and a context summary. It does not itself enforce later-wins/local-wins policy.
6. It is described in documentation, but absent from the installed v1.1.0 CLI help and not found as a matching implementation in the inspected source. Treat as unverified/preview, not a working stable command.
7. No. The documented agent artifact compiles coordinator behavior and explicitly omits live state such as decisions, histories and skills. Use a snapshot or ordinary versioned state files when preserving that information is required.
