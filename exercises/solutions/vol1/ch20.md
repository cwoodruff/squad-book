# Chapter 20 Solutions

## Exercise Solutions

1. Any scenario is acceptable if the choice follows repository maturity, ownership, contributors, and risk. A solo developer should prioritize review and tests; a new project should begin with a small vertical slice; an existing repository should start with evidence-based exploration; mid-project adoption should map current reality and rationale; open source should prioritize governance and least-privilege automation.
2. A complete recipe states repository root/branch, clean-worktree check, `squad init` and review of generated files, exploration/plan, a bounded first task, file scope, explicit acceptance criteria, project test command, and a human reviewer. Include a stop condition if the agent discovers unexpected architecture or risky files.
3. API contract work and independently scoped UI presentation may be parallel only after agreeing the task JSON/status shape, endpoint, error behavior, and compatibility. A backend agent can add route/test behavior while a frontend agent prepares UI against the agreed contract; integration tests or a reviewer must validate the combined behavior. Avoid both agents editing the same files or inventing different interfaces.
4. Example checklist: restrict workflow triggers to approved labels/events; reject or exclude security/private issues; pin permissions to only required read/write scopes; use repository secrets with least privilege; limit eligible files/branches; run tests; prevent automatic merge; require a maintainer review; document opt-out/escalation; and inspect action dependencies and branch checkout behavior.
5. A stable architectural choice with rationale belongs in a decision. A reusable implementation/testing convention belongs in a skill. A one-time observation such as “the test runner took 12 seconds today” should not be retained unless it becomes an actionable trend or operational baseline.

## Quiz Answers

1. Exploration reveals actual architecture, tests, and conventions, reducing harmful guesses and helping keep the first change in scope.
2. It validates team fit and assumptions with low risk before broadening delegated work or automation.
3. Open source, because issues and PRs are public/untrusted inputs and automated permissions can affect contributors and project security.
4. No. Initialization creates project artifacts; it does not prove that workflows exist, are active, properly permissioned, or safe.
5. Run the exact test command and report its result/output; a summary alone is not evidence.
6. The solo operator remains accountable for correctness, security, and accepting the change; the agent is not an independent authority.
7. Confirm whether the state is tracked or external, compare backup and current revisions, preserve newer changes, and validate the restore on a copy or branch before overwriting active state.
