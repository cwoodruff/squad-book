# Chapter 19 Solutions

## Exercise Solutions

1. An intermittent 503 is transient: use bounded backoff, record attempts, and escalate after the retry limit. A deterministic assertion failure calls for diagnosis and a targeted fix, with a maximum of three fix/retry cycles. An unavailable optional report section may permit graceful degradation if it is genuinely noncritical and is clearly disclosed. A push blocked by branch protection is an authorization/policy boundary: stop and escalate or follow the approved process; never force-push around it.

2. A stronger prompt might be:

   ```markdown
   ## Task
   Add or adjust one integration test in `api/test/app.test.ts` for invalid task status handling. Do not change unrelated endpoints.

   ## WHY this matters
   Tasktrack must reject invalid state transitions so clients cannot create task records with unsupported status values.

   ## Success criteria
   - [ ] The test checks the HTTP status and relevant response contract.
   - [ ] The implementation changes only if the current behavior violates the contract.
   - [ ] `npm test` passes and the result is reported.

   ## Escalation path
   If expected behavior is unclear or the test already passes, report the evidence and propose a narrow next case; do not invent a new API contract.
   ```

3. “Cycle 1 added invalid-status coverage but omitted the unknown-task-ID case. Add a test for `PATCH /tasks/:id` with a valid status and a nonexistent ID; assert the documented 404 response, preserve the invalid-status test, and run `npm test`. Report whether the current behavior already satisfies the contract.” Cycle three should state what cycle two attempted, all remaining unmet criteria, prior test output, and a final stop condition. If it still cannot converge, escalate rather than start cycle four.

4. The new revision owner examines the failing test output and diagnoses the behavior, with a targeted fix and verification. The original author remains locked out of the rejected artifact and must not advise or pair on the revision. If the new author is also rejected, they become locked out for the next revision cycle. A different eligible specialist takes the next cycle, or the coordinator escalates when all are exhausted.

5. The template describes a model-selection fallback chain and CLOSED/OPEN/HALF-OPEN cooldown behavior. The SDK `PredictiveCircuitBreaker` instead records quota samples and estimates exhaustion; it does not automatically pick a lower-cost model. Do not claim that v1.1.0 CLI Ralph automatically activates the template's PowerShell state machine or that the SDK predictor switches model IDs on rate limit.

## Quiz Answers

1. A transient failure such as a timeout, network error, or rate limit, provided the operation is safe to retry.
2. Attempts made, exact error messages, known facts, likely cause, unresolved uncertainty, and the specific decision/access/specialist needed.
3. `Task`, `WHY this matters`, `Success criteria`, and `Escalation path`.
4. Three cycles maximum. If cycle three does not meet criteria, escalate with the attempt history and remaining gap; there is no cycle four.
5. Validation confirms success criteria, detects skipped work or regressions, and resolves or escalates uncertainty before accepting the result.
6. No. The original author stays locked out of that artifact's revision after rejection.
7. Backoff schedules a delayed retry; an open circuit temporarily stops requests to avoid adding pressure to an unhealthy dependency.
8. No. It predicts quota exhaustion and reports whether the caller should open/pause; model selection is not implemented by that SDK class.
