# Chapter 7 Solutions

## Exercise Solutions

1. **Due-date issue:** Include a concrete request such as `GET /tasks?dueBefore=2026-11-01`, show a representative response with due dates, and state that authentication changes are out of scope. Specify that an invalid date returns `400` with a stable error shape and a test. The request/response makes the API contract observable; the non-goal limits scope; the error criterion makes edge behavior reviewable.
2. **Bug form:** Use required fields for reproduction steps, expected behavior, and actual behavior because a maintainer needs enough evidence to confirm the defect. Make Node.js version required only if runtime compatibility is relevant; otherwise make it optional. A concise template could use `textarea` fields for reproduction and behavior plus an `input` for the runtime version.
3. **Minimal labels:** `go:yes` / `go:no` / `go:needs-research` for disposition, `release:backlog` for release targeting, `type:feature` / `type:bug` for category, `priority:p0` / `p1` / `p2` for urgency, and `squad:backend` / `squad:tester` for ownership. These names are conventions. The `squad` base label is an operational input to the default Watch issue scan, and member labels participate in routing; enforcement and synchronization require workflows that are installed and enabled.
4. **Board behavior:** Dragging an issue into Ready does not automatically apply `go:yes` by convention alone. A webhook or workflow that receives the project event, maps the new status to a label, and has permission to edit issues would be needed. In v1.1.0, `squad watch --board` offers limited project lifecycle handling and reconciliation; it does not promise general bidirectional drag-to-label sync or arbitrary custom-field mappings.
5. **Issue vs. chat:** Preserve outcome, current behavior, acceptance criteria, constraints/non-goals, relevant error evidence or file paths, dependencies, and test expectations. Keep the issue concise enough to stay usable and ask for clarification if a missing detail changes the design or scope.

## Quiz Answers

1. An open issue must carry the `squad` label to be included by the default Watch issue scan.
2. GitHub interprets and renders the issue-form YAML. Squad later reads the created issue through its platform adapter.
3. Acceptance criteria should name observable behavior and a way to verify it, such as a test case or expected API response. They should distinguish required outcomes from non-goals.
4. No. Namespaced labels are ordinary GitHub labels. Exclusivity requires a workflow or another enforcing process.
5. The v1.1.0 `--board` capability makes best-effort `gh project` calls for lifecycle status and certain closed/open mismatches. It does not create a complete board, implement arbitrary label/custom-field mappings, or provide general two-way drag-and-drop synchronization.
6. It assumes GitHub Agentic Workflows (`gh-aw`) and its dispatcher, implementation-worker, and advisory-reviewer workflows, plus the associated structured artifact conventions.
7. No. Issues do not isolate working directories. Use worktrees or serialize overlapping changes.
