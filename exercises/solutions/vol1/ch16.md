# Chapter 16 Solutions

## Exercise Solutions

1. **Choose tiers.** A routine endpoint change needs the current task and active decisions (hot), but not necessarily old sessions or a wiki. Resuming a failed migration needs hot context plus the relevant cold summary of what already happened; a stable migration contract or architecture reference could be wiki-like. Implementing against an API contract needs hot context and the specific durable contract; cold history is useful only if prior attempts or design decisions affect the work. In v1.1.0 these are reasoning categories, not built-in tier flags.

2. **Write a reflection.** Example: `[HIGH] Preserve HTTP 400 when PATCH receives a status outside todo/doing/done. Evidence: user correction, “Please keep invalid status values as HTTP 400; clients depend on that response.” Candidate destination: a reviewed team API decision if the contract is shared, plus the test that proves the behavior. Not persisted yet.` It retains the correction and points to evidence without claiming an unperformed write.

3. **Predict a nap.** A history larger than 15 KiB is eligible for compression if it has more than five relevant `##` sections. Ordinary nap keeps the core context section and the newest five sections and appends older sections to `history-archive.md`. It does not compose a new semantic summary: it selects Markdown sections structurally and moves older text to an archive. An eight-section file would leave three older sections to archive, subject to the implementation’s section parsing.

4. **Review a decision archive.** Undated entries are kept because they may be foundational rules and the algorithm cannot reliably determine their age. Safeguards include checking that the archive destination can be committed before removing source content and verifying the expected entry count after append. The code also uses fence-aware heading detection so headings inside fenced examples do not split entries.

5. **Recover safely.** Inspect the current branch/worktree, issue list and any orchestration log/session history; confirm whether the issue exists and whether it is open or already assigned; compare persisted files with the intended plan; identify the next incomplete step; determine whether the next operation is idempotent. Re-creating an issue can produce duplicate external work because the earlier create may have succeeded even though its result disappeared from the conversation. The documented session checkpoint mechanism is not verified as implemented in v1.1.0, so rely on observable state.
