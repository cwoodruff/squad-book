# Chapter 21 Solutions

## Exercise Solutions

1. **Repository boundary map:** A strong answer names the repository root, one entry point, two bounded modules and their consumers, the shared dependency, focused tests, and a known verification command. The discovery request should explicitly forbid edits and require path evidence, for example: “Map `services/billing` only. Identify its HTTP entry point, persistence adapter, imports from `shared/contracts`, and tests. Cite the file paths and tell me which test command exercises the route. Do not modify files. Separate confirmed facts from assumptions.” The exact map depends on the repository; the goal is useful evidence rather than exhaustive file enumeration.

2. **Monorepo route design:** One reasonable team has a coordinator, an auth/billing backend specialist, a web specialist, and a tester. Route `services/auth/**` and `services/billing/**` to the backend owner; route `web/**` to the frontend owner; route `shared/contracts/**` to the coordinator for consumer discovery and contract agreement. Have the responsible service specialists review shared changes, and require tests that validate both producer and consumer behavior. A separate integration-test role is useful only if it represents recurring independent work.

3. **SubSquad partition review:** Example: `api` uses label `team:api`, scope `api/`, workflow `branch-per-issue`; `web` uses label `team:web`, scope `web/`, same workflow. Cross-cutting issues include changing the task JSON contract consumed by both API and browser client, and adding authentication or persistence that changes both server and UI behavior. Route those through a coordinator or keep them unassigned until a human decides how to split the work. Folder scope is guidance, not a write lock.

4. **Human decision gate:** Ask an agent to compare the migration options on compatibility, rollback, operational risk, testability, and data loss. It should make no schema or application changes until the named maintainer chooses one. Record the decision with date, decision-maker, chosen option, rationale, and any conditions in the shared decisions log. The human reviewer should inspect migration and rollback scripts, tests for old and new data, application compatibility, and the final diff. A route instruction alone does not enforce the pause, so relay the decision manually and protect merge with repository rules.

5. **Capability boundary audit:** Example classification: “Only handle issues labeled `team:api`” is an issue filter; “focus on `api/`” is an instruction/scope hint; “create one branch per issue” is a Git workflow; branch protection and required reviewers are GitHub-enforced controls; a container mount or OS permissions can constrain filesystem access. Any description of `folderScope` as preventing writes outside its paths is a mistaken enforcement claim.

## Quiz Answers

1. Scoped discovery limits irrelevant context and provides time to understand the important module contracts. It can produce a verifiable path-backed map, whereas a blanket request can waste context and still miss relevant dependencies.
2. A single Squad with specialists is a better starting point when services share product goals, decisions, state, and review culture, and cross-service coordination is common.
3. `labelFilter` partitions issue candidates by issue label. `folderScope` does not enforce a filesystem write boundary or sandbox.
4. `.squad/workstreams.json`; the top-level list is named `workstreams`.
5. `SQUAD_TEAM` environment variable, then `.squad-workstream`, then auto-select if exactly one SubSquad is configured, then no active SubSquad/single-Squad behavior.
6. No. A human roster entry does not create an AI agent session or guarantee notification; the user must route the question through the real communication channel and relay the response.
7. Branch protection and required human PR reviewers (also code-owner rules or OS/container permissions) are stronger controls than routing prose.
